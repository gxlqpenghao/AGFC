# PDF AGFC 开发指导文档

## 1. 问题背景

当前在 [`_pdf_healer_pipeline`](/Users/paul/Documents/AI协作/中建科技进步奖/_pdf_healer_pipeline) 中尝试过基于双轮 VL 的图片修复路线，但已经暴露出明显瓶颈：

1. `MinerU` 默认图片抽取对常规文档通常可用，但对以下 PDF 场景存在系统性缺陷：
   - 矢量图由多个对象拼接形成
   - 一张逻辑完整图由多个子面板、虚线框、彩色说明条共同组成
   - 图与正文距离很近，甚至上下直接相邻
   - 图中含有公式、图表、示意图、流程箭头和文本混合表达

2. 直接让通用 VL 模型返回最终 bbox 不稳定：
   - 容易把一张逻辑完整的大组图裁成局部
   - 容易把图外正文一起带入最终图片
   - bbox 既有语义漂移，也有几何漂移

3. 一旦为了修补这些问题而继续增加 prompt 约束、cleanup 回合或几何例外逻辑，就会再次走向“软规则堆叠”，通用性越来越差。

因此，这个问题不能继续被视为“如何让模型返回更准的 bbox”，而应被重新定义为：

> 如何从 PDF 页面中恢复“逻辑完整图”的边界与组成，而不是恢复一个看起来差不多的矩形框。

## 2. 我们拟解决的关键技术问题

本项目拟解决的核心技术问题是：

### 2.1 如何避免将一张逻辑完整图拆碎

重点不是让图片数量与 sidecar 完全一致，而是避免以下错误：

- 一张逻辑完整的海报式组图被拆成多张小图
- 并列子面板明明属于一个整体，却被分别导出
- 同一组图的底部说明条、共享标题或图注被错误排除

### 2.2 如何精准隔离正文污染

要稳定排除以下内容：

- 章节正文段落
- 图外长句说明
- 参考文献样式文本
- 论文题目或小节标题

同时要保留以下图内内容：

- 图题、图注、图例
- 坐标轴文字
- 子图标签
- 共享彩色说明条
- 虚线框内的面板说明

### 2.3 如何让语义判断与几何求解分离

我们希望避免“让 VL 同时负责看懂内容和给出最终几何边界”这一耦合。  
新的路线必须做到：

- 语义判断：由 VL 或后续自研判别器负责
- 几何求解：由我们自己的工作流稳定完成

## 3. 核心创新点

本项目的关键创新点不是换一个更大的 VL 模型，而是重新定义问题形式。

## 3.1 核心创新：AGFC（Atom-Graph Figure Closure）

### 定义

AGFC = `Atom-Graph Figure Closure`

中文可表述为：

> 基于页面原子图闭包的 PDF 逻辑图恢复方法

### 基本思想

不再要求模型直接返回最终 bbox，而是先把 PDF 页面拆成“原子”，再让模型只判断这些原子之间的关系与归属，最后由算法求出逻辑完整图的闭包。

也就是说：

- 旧问题：`page image -> VL -> bbox`
- 新问题：`page -> atoms -> graph -> semantic judgement -> closure -> export`

### 为什么这是核心创新

因为在 PDF 中，一张图往往并不是一个对象，而是多个对象的组合：

- text block
- equation
- vector path
- image xobject
- panel border
- color band
- connector
- chart region

如果继续用 bbox 直接建模，就会天然丢掉这种“组合结构”的信息。  
而 AGFC 将图定义为：

> 页面原子图中的一个语义闭包子图

这使得“组合图完整性”和“正文隔离”可以在同一个统一框架下处理。

## 3.2 第二创新：语义裁决与几何求解解耦

VL 不再直接输出最终几何框，而只回答高层问题：

- 这个原子是否属于图？
- 这两组原子是否应该合并？
- 这段文本是正文还是图内说明？

几何框、导出区域、最终合并边界全部由工作流自己完成。  
这样可以显著降低：

- bbox 漂移
- prompt 偶然性
- 模型回框不稳定

## 3.3 第三创新：从“元素识别”转为“逻辑图闭包”

我们并不追求严格复制 `sidecar` 的元素个数。  
我们的目标更符合 PDF 场景：

- 允许若干物理并列小图被合并成一张大图
- 但不允许一张逻辑完整组图被拆成多张碎图

这是一种更符合 PDF 版式和工程使用场景的抽图定义。

## 4. 技术路线

## 4.1 第一阶段技术栈（先做工作流）

### PDF 原生解析

- `PyMuPDF`
  - 读取 PDF 页面
  - 提取文本块、绘图对象、位图对象
  - 高 DPI 渲染页面和导出图片

### 视觉分析

- `OpenCV`
  - 连通域分析
  - 边框检测
  - 色带/面板区域检测
  - 面板候选提取

- `Pillow`
  - 图像裁切
  - 调试图保存

- `NumPy`
  - 图像矩阵运算
  - 掩膜与统计计算

### 几何与图建模

- `Shapely`
  - 多原子区域 union
  - 包含、相交、邻接几何运算

- `NetworkX`
  - 页面原子图构建
  - 闭包扩展与子图求解

### 语义裁决

- `Qwen VL`
  - 第一阶段作为关系判定器使用
  - 不再负责最终 bbox 生成

### 数据结构与调试

- `dataclasses` / `pydantic`
  - 原子、边、候选组、闭包结果结构化表示

- `JSON / JSONL`
  - 中间结果落盘
  - 可追溯调试

## 4.2 第二阶段可沉淀为自研模型的部分

当工作流稳定后，可逐步将以下判断蒸馏为我们自己的小模型：

1. `body_text vs figure_text` 判别器
2. `should_merge(panel_a, panel_b)` 合并判别器
3. `belongs_to_figure(atom)` 原子归属判别器

也就是说，最终产品形态是“工作流系统”，但关键语义节点会逐步沉淀成我们自己的模型。

## 5. 第一版系统模块设计

建议在本目录中逐步形成如下模块：

### 5.1 `pdf_agfc_atoms.py`

负责页面原子化：

- text_block
- equation_block
- raster_image
- vector_cluster
- panel_border
- color_band
- connector_arrow
- chart_region

输出统一 atom schema。

### 5.2 `pdf_agfc_panels.py`

负责构建 panel / region 候选：

- 虚线框识别
- 共享底部说明条识别
- 同行/同列面板聚类
- 初始候选图块提议

### 5.3 `pdf_agfc_graph.py`

构建页面原子图：

- 节点：原子
- 边：空间关系、包含关系、视觉连接关系、共享说明关系

### 5.4 `pdf_agfc_vl_judge.py`

对有歧义的关系调用 VL：

- belongs_to_figure?
- should_merge?
- body_text_or_figure_text?

### 5.5 `pdf_agfc_closure.py`

从 seed candidate 出发求闭包：

- 吞并同组子面板
- 吞并图内说明条
- 排除正文段落
- 得到最终 figure atom set

### 5.6 `pdf_agfc_export.py`

将闭包结果导出为最终图片：

- union geometry
- final crop region
- high DPI export
- 调试可视化

### 5.7 `run_pdf_agfc_v1.py`

整体 orchestrator：

1. 读取 PDF
2. 页面原子化
3. 构图
4. 调用语义裁决
5. 求闭包
6. 导出图片
7. 输出调试信息

## 6. 实施计划

## 阶段 A：问题形式验证

目标：

- 验证“原子图闭包”比“直接 bbox 回归”更适合这个问题

实施内容：

1. 在当前样本 PDF 上完成页面原子提取
2. 导出页面 debug overlay
3. 手工检查原子是否能覆盖：
   - 组图面板
   - 底部说明条
   - 正文段落

阶段产物：

- `atoms.json`
- `overlay_debug.png`

## 阶段 B：panel 与候选图块生成

目标：

- 构建不容易把大图拆碎的候选图块集合

实施内容：

1. 识别虚线框、统一色带、共享说明条
2. 根据版式结构构造 panel groups
3. 为每页生成候选 figure groups

阶段产物：

- `panel_groups.json`
- `candidate_figures.json`

## 阶段 C：VL 关系裁决

目标：

- 让 VL 只做“归属与合并判断”

实施内容：

1. 设计三个标准问题：
   - 这个原子是否属于图？
   - 这两组原子是否应合并？
   - 这段文字是不是正文污染？
2. 记录所有 query / response
3. 建立失败案例集

阶段产物：

- `vl_judgements.jsonl`
- `error_cases/`

## 阶段 D：闭包求解与最终导出

目标：

- 输出稳定的逻辑完整图

实施内容：

1. 以 panel candidate 为 seed
2. 根据关系图向外闭包
3. 排除正文原子
4. 进行 union geometry 求解
5. 高 DPI 导出

阶段产物：

- `final_images/`
- `closure_debug.json`

## 阶段 E：小规模评测与规则冻结

目标：

- 冻结第一版工作流接口

评测重点：

1. 是否还会把一张逻辑完整图拆碎
2. 是否仍会把正文带入图
3. 是否能稳定保留底部说明条、图题、图注

完成标准：

- 大组图拆碎错误显著下降
- 正文污染显著下降
- 与现有 `v11` 相比，错误类型更可解释、更可调试

## 7. 开发原则

1. 不再继续堆叠 bbox prompt 和 cleanup 特例。
2. 不再把 `MinerU` 默认图片裁图作为特殊 PDF 的真值。
3. 不追求与 sidecar 图片数量完全一致。
4. 优先保证：
   - 逻辑完整图不被拆碎
   - 正文不被混入
5. 先做工作流，后沉淀自研模型。

## 8. 当前结论

本项目的第一性目标不是“让模型回一个更准的框”，而是：

> 建立一条能够恢复 PDF 中逻辑完整图的结构化工作流。

这条路线的核心壁垒不是简单调用某个现成模型，而是：

1. 我们如何定义页面原子
2. 我们如何建立原子关系图
3. 我们如何求出逻辑图闭包
4. 我们如何把这些关系判断逐步沉淀成自己的模型

如果这条路线走通，它不只是当前这一份 PDF 的修补方案，而会成为我们后续处理复杂 PDF / PPT 图片抽取问题的基础能力。
